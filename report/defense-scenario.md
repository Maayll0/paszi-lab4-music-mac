# Сценарий защиты MusicAccess

Продолжительность демонстрации: примерно 7–10 минут. Цель — показать работу сервиса и подтвердить, что решение о доступе принимает backend по меткам из БД.

## Подготовка

1. Запустить Docker Desktop, затем из корня проекта выполнить `docker compose up --build`.
2. Проверить `docker compose ps` и открыть http://localhost:8080.
3. Взять пароли `demo_public`, `demo_confidential`, `demo_secret` из локального `.env`. Не показывать файл на экране при записи отчёта.
4. Открыть DevTools → Network. Перед проверкой отказа очистить список запросов. Для каждого запроса показывать URL, статус и тип ответа, не cookie и токены.

## 1. Регистрация и сессия

- Зарегистрировать отдельного пользователя с уникальным логином, email и установленным чекбоксом музыкального аккаунта.
- Показать успешное сообщение; повторить регистрацию того же логина и получить 409.
- Показать отказ слабому паролю в форме. Чтобы продемонстрировать именно серверный 422, использовать запрос из README со слабым паролем: клиентская проверка формы не отправляет такой запрос.
- Войти новым пользователем: шапка показывает логин и PUBLIC. Обновить страницу — вход сохраняется.
- Объяснить: email и чекбокс не влияют на допуск. Пароль проверяется через Argon2id, браузер получает HttpOnly cookie, а профиль восстанавливается через `/api/me`.

Кадры: регистрация, успешный результат, ошибка занятого логина, шапка после обновления страницы.

## 2. Поиск и URL

- В каталоге ввести `Night`, показать подсказку и перейти к Night Drive.
- Открыть `/music?title=Night&artist=Electronic`: должен остаться один трек.
- Сбросить фильтры, нажать браузерную кнопку «Назад»: фильтры и результат восстанавливаются.
- Ввести отсутствующее название, показать сообщение о пустом результате.

Объяснить: общий поиск использует OR по названию и исполнителю, отдельные фильтры — AND. Запрос отправляется после задержки 350 мс; SQL формирует ORM, а не URL.

Кадры: подсказки и адресная строка с двумя фильтрами.

## 3. Матрица мандатного доступа

Для каждой строки выйти из предыдущего аккаунта и войти под указанным логином. Открывать треки из каталога и нажимать «Слушать».

| Аккаунт | Night Drive / Public | Deep Ocean / Confidential | Secret Sessions / Secret |
|---|---|---|---|
| demo_public | играет | 403 | 403 |
| demo_confidential | играет | играет | 403 |
| demo_secret | играет | играет | играет |

Для разрешённого трека показать воспроизведение, паузу, перемотку и громкость. Для Secret показать переключение между доступными треками. В Network разрешённый Range-запрос к `/api/tracks/{id}/stream` имеет статус 206; полный запрос может иметь 200.

Для Public → Confidential показать одновременно страницу `/access-denied` и ответ `/stream` со статусом 403. В теле отказа — JSON, аудиобайтов нет. Каталог продолжает показывать метаданные закрытых треков: защищается аудио, а не название.

Объяснить формулу: `user.clearance_level >= track.security_level`. Функция `require_read_access` в `backend/access.py` вызывается серверным endpoint потока. Метки загружаются из БД при каждом запросе, включая перемотку. Значение допуска в JavaScript не является доказательством доступа.

## 4. Завершение сессии и удаление

- Во время воспроизведения нажать «Выйти»: плеер исчезает, шапка меняется без перезагрузки.
- Открыть URL аудиопотока без сессии: ожидается 401, даже для Public.
- Войти отдельным пользователем, созданным в начале демонстрации. Через ссылку с логином открыть аккаунт, подтвердить пароль и удаление.
- После удаления снова войти тем же логином: вход отклоняется. Для этой проверки не удалять демонстрационные аккаунты.

Объяснить: выход отзывает текущую сессию, удаление аккаунта — все его сессии. Повторный вход в том же браузере заменяет cookie и CSRF-токен; прежние значения больше не работают.

## 5. База данных и автоматические проверки

Показать запросы из README к `users` и `tracks`. Для паролей выводить только префикс `password_hash`: `$argon2id$`. Показать три уровня допуска и метки треков.

Из корня проекта выполнить:

```powershell
backend/.venv/Scripts/python.exe -m pytest -q
```

Локальный набор после расширения проверок сессий содержит 31 тест. Он проверяет в том числе все девять сочетаний MAC, HTTP Range, смену сессии и CSRF при повторном входе, а также передачу Secure-cookie только по HTTPS. Для PostgreSQL и контейнеризации показать успешные задания GitHub Actions; они являются отдельной проверкой от локальных SQLite-тестов.

## Короткие ответы на вопросы

- **Почему это MAC?** Решение основано на доверенных метках допуска и секретности, а не на роли пользователя или чекбоксе.
- **Можно ли повысить допуск через регистрацию?** Нет. Сервер назначает PUBLIC; дополнительные поля допуска отклоняются с 422.
- **Почему закрытые названия видны?** Метаданные каталога публичны; защищённый ресурс — аудиофайл.
- **Почему после выхода файл нельзя запросить снова?** Сессия отозвана на сервере. Уже полученные разрешённые байты из памяти клиента отозвать нельзя.
- **Почему локальная cookie без Secure?** Локальная демонстрация использует HTTP. В `APP_ENV=production` включён Secure, и нужен HTTPS.
- **Кто назначает повышенные допуски?** Доверенный seed-скрипт создаёт демонстрационные аккаунты; публичного API повышения допуска нет.
